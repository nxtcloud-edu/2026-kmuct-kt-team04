# Persistent TravelRoute creation, display, and editing

The travel map now persists calculated car directions, displays saved geometry from watcher state, and lists routes beneath their origin pins. A dedicated editor supports geometry-preserving name changes, recalculation, and deletion with versioned mutations. Endpoint validation keeps new routes inside the selected time block, and unsupported transport modes remain fail-closed. **Watch for: [confirmed] a completed save can erase a newer planning session, [likely] the route can disappear between mutation success and watcher delivery, [confirmed] a clicked saved route can remain hidden behind an active calculation preview, and [confirmed] these lifecycle paths have no UI-level automated coverage.**

**Verdict**: NEEDS_CHANGES

## High-level view

Route creation persists the chosen car result under a UUID request ID and then relies on watcher state for the saved geometry. Because the calculation preview is cleared immediately after the mutation, continuous display depends on the subscription refresh arriving first.

A newly selected time block defaults to its first saved route and allows that route to be dismissed. Sidebar route rows also select and edit a saved route, but calculation-preview precedence can leave the map showing a different route than the open editor.

The save flow remains interactive while its mutation is pending, allowing later block/planner state to be overwritten by the older completion. Build, lint, and all 17 existing tests pass, but none covers the route UI state machine.

1. **Stale save completion** — **[confirmed]** A save started in one block can later close and reset a newer planning session in another block. Lock the relevant controls or ignore completion-side UI updates when the active session token no longer matches.
2. **Watcher handoff display gap** — **[likely]** Clearing the calculated route before watcher state contains the saved UUID can temporarily remove the route from the map. Retain the preview until the persisted route is observed, or refresh and switch only after it is present.
3. **Saved route masked by preview** — **[confirmed]** Clicking a saved route opens its editor while an active calculation can keep different geometry on the map. Clear/suspend the preview or prioritize the selected saved route while editing.
4. **Route UI coverage gap** — **[confirmed]** No automated test covers creation, watcher handoff, block-switch races, saved-route selection, or editor actions. Add component/integration tests around these lifecycle paths.

<details>
<summary>Details</summary>

## Save completion can cancel work started in another time block

While `room.createRoute` is pending, only the save button is disabled; block navigation and planner close/reopen/restart remain active. Its eventual success unconditionally calls `setRouteOpen(false)` and `resetRoute()`, discarding endpoints or results created after switching blocks. This is **[confirmed]** in `TravelMapPanel.tsx:183-209` and `RoutePlanner.tsx:43-77`. Lock the workflow during save or gate completion-side state changes with a session/block generation token.

## Mutation-to-watcher handoff can temporarily remove the route

Success immediately clears `selectedRoute`, while its replacement is available only after `room.state.routes` receives the subscription-driven refresh. Live watcher delivery is asynchronous and falls back to a 15-second recovery poll, so a visible gap is **[likely]** between mutation response and watcher state (`TravelMapPanel.tsx:52-63,186-194`; `src/lib/backend.ts:114-142`). Keep the successful preview until the matching saved UUID appears, then hand display ownership to the persisted object.

## Saved-route selection is masked by an active calculation preview

`handleSelectStoredRoute` changes the saved selection and opens its editor, but `displayedRoute` always prefers `selectedRoute`. With a calculation preview present, the map therefore disagrees with the clicked row and editor. This is **[confirmed]** in `TravelMapPanel.tsx:63,211-213`; selecting a saved route should clear/suspend the preview or temporarily take display priority.

## Route lifecycle coverage stops below the UI boundary

No test references `TravelMapPanel`, `RoutePlanner`, `ScheduleSidebar`, or `RouteEditorDialog`, a **[confirmed]** gap for default display/dismissal, watcher replacement, pending-save block changes, preview-versus-saved selection, and name/recalculate/delete payloads. The existing 17 backend-oriented tests do not exercise these behaviors.
